### 2.2 写模块的门槛 —— 比预想低

- 一个**完整可用**的模块（含面板 SVG、Widget、注册）= **103 行**（官方 `Blank.cpp` 已通读）
- 加一个模块只需动**三处**：
  1. 新建 `plugins/我的包/` 目录（模块 + 面板）
  2. `plugins/plugins.cpp` 加一个 `initStatic__我的包()` 注册函数
  3. `plugins/Makefile` —— 加 `PLUGIN_FILES += $(wildcard 我的包/src/*.cpp)` 与包专属编译规则块
     > ⚠️ **2026-09-21 修正**：旧文此处写的是 `Makefile.base.mk`，**那个文件在 `dpf/` 和仓库根，与插件无关**。
     > ⚠️ **2026-09-21 二次修正**：`PLUGIN_FILES` **并非全局都用 `$(wildcard ...)`** ——
     > 官方内置包（`Cardinal` 段 L226–239）是**显式逐行列文件**，只有部分第三方包（Biset L581）用 wildcard。
     > ⇒ **新建自己的包**照 Biset 写 wildcard，新增源文件才不必改列表；**往官方包加文件必须手工加行**。
     > 详见 `docs/BISET-REFERENCE-MAP.md` §6。
- 现有 **170 个插件包**的写法可以直接抄，不用从零摸索

## 三、缺口清单（3 个）

### 缺口 1 · WSL 里跑 Cardinal 出不了声 ⚠️

- **现象**：GUI 程序启动后秒退，日志只有一句 `Communication error with the JACK server`
- **已排除的原因**：jackd 服务器能起来（realtime 模式），`jack_lsp` **能连上**并列出 4 个端口；
  内存锁上限已提到 `unlimited`；`/dev/shm` 有 5.8 GB 空闲 —— **这三个都不是原因**
- **已定位到**：报错出自 `dpf/distrho/src/DistrhoPluginJACK.cpp:1075`，
  走的是 `jackbridge`（DPF 自己写的桥接层，绕开 libjack 直连）
- **判断**：这是 DPF 桥接层与 jackd2 的兼容问题，**继续挖成本不可控，建议不挖**
- **附带硬伤**：WSLg **只桥图形和音频，不桥 MIDI** —— 就算修好音频，键盘信号也进不来；
  且 GL 是**软件渲染**（`llvmpipe`，无 GPU 加速），界面会卡

### 缺口 2 · 没有虚拟 MIDI 端口 ⚠️

- 本机 MIDI **输入端口 0 个**，输出端口 1 个（Microsoft GS Wavetable Synth）
- **影响**：企划 1（把扒出的谱喂给 Cardinal）和企划 3（AI 生成练习曲）都缺「注入音符」的管子
- **补法（二选一）**：
  - 装虚拟 MIDI 端口软件（loopMIDI 一类，免费，Windows 侧）
  - 自写一个「MIDI 文件播放模块」（复用 2.4 里那个已存在的 smf 库）

### 缺口 3 · Windows 版 Cardinal 还没编过 ⚠️

- 工具链验证过了（能出 exe），但 **PawPaw 完整交叉编译还没跑**
- PawPaw 的工作量：从源码下载并编译**几十个库**（libpng / libxml2 / freetype / cairo / glib / fftw / …）
  成 Windows 静态库，再编 Cardinal 本体
- 前置条件：需要装 **wine**（用于跑 Windows 版的构建工具）

## 四、岔路口 —— 请你拍板

**决策点：开发期「改代码 → 听声音 → 调参数」这个循环，在哪儿跑？**

### 路线 A · 交叉编译出 Windows 版 Cardinal

- **做法**：装 wine → PawPaw bootstrap → `make` win64
- **代价**：装 wine（1 GB+ 依赖）；bootstrap 编译几十个库（**估计 30-60 分钟**）；
  Cardinal 全量交叉编译（**估计 20-40 分钟**）。一次性投入，之后增量编译仍很快。
- **收益**：**产出完整 Windows 版 Cardinal**，可直接与现有安装对照/替换；音频、键盘全部原生正常
- **风险**：低 —— 官方 CI 就是这条路径发布的

### 路线 B · 先用 VCV Rack 开发模块，完成后再搬进 Cardinal

- **做法**：装 VCV Rack（免费），用 Rack SDK 编插件 DLL。**Rack 支持热加载**，改完即可听
- **代价**：多装一个 VCV Rack；插件与 Cardinal 可能存在细微差异需适配
- **收益**：**开发循环最快**（这是社区公认的开发方式，VCV 模块代码搬进 Cardinal 通常能直接编过）
- **风险**：中 ——「代码一行不改」是社区经验，不是官方保证

### 路线 C · 继续修 WSL 的音频

- **代价**：不确定（可能一小时也搞不定）
- **收益**：开发不离开 WSL
- **硬伤**：**键盘 MIDI 进不来 + 软渲染卡** → 就算修好，也只能看界面、不能弹

> **补充信息（影响判断）**：Cardinal 是**静态插件加载器** —— 模块在**编译期焊进主程序**，
> 没有运行时动态加载。所以「我写一个模块 → 你就能用」这件事，**必须先重新编译一次 Cardinal**。
> 这是 VCV Rack 与 Cardinal 最大的区别，也是路线 A 绕不过去的根本原因。

## 六、我的技术判断（供参考，决定权在你）

- **路线 A 是必经之路**：因为 Cardinal 是静态加载，写模块就必须重编一次；而最终产物必须是
  Windows 版（你的键盘、音频、工作流都在 Windows 侧）。区别只是**早做还是晚做**。
- **路线 B 是加速器，不是替代品**：它能让你在模块的**音乐逻辑**上迭代得更快，
  但最后仍要走一次 A 才能变成 Cardinal 能用的东西。
- **路线 C 性价比最低**：投入不可预测，且有两个先天缺陷（键盘进不来、软渲染卡）。

如果要我给一个执行顺序：**先把 3 件小事做掉（插键盘 / 装虚拟 MIDI / 定数据格式）**，
这三件不依赖任何决策、当天能完成；同时再定 A 还是 A+B。
