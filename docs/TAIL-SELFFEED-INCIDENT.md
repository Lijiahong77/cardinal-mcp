# 一个 shell 反模式如何吃光 96 GB 磁盘：uutils `tail` 自噬事件复盘

> 记录时间：2026-09-20
> 环境：WSL2 / Ubuntu 26.04 / `tail (uutils coreutils) 0.8.0`
> 后果：一个日志文件在 **2 分 7 秒**内涨到 **96.6 GB**，把 451 GB 的宿主磁盘塞满，虚拟机无法启动。
> 结论：这是 **uutils coreutils 独有的行为**（GNU 9.4 / 9.7 均正常）。

---

## 1. 摘要

一句脚本写法 —— **把命令的输出追加到它正在读的那个文件** —— 在新版 `tail` 上会形成正反馈循环，以约 760 MB/s 的速度无限自我复制。

```bash
{
  grep -c 'error' "$LOG"        # 读 LOG
  grep 'error' "$LOG" | head -15
  tail -10 "$LOG"               # 读 LOG
} >> "$LOG"                     # 整块输出又写回 LOG
```

GNU 的 `tail` 在这种写法下只追加一次就停；**uutils 的 `tail` 会一直读到"真正的文件末尾"——而那个末尾在不断后退，于是永不停止。**

---

## 2. 现场证据

| 证据 | 数据 |
|---|---|
| 文件大小 | `96,604,475,392` 字节（96.6 GB） |
| 增长耗时 | 20:05:53 → 20:08，约 **127 秒** |
| 平均写入速度 | 约 **760 MB/s**（纯写入循环才可能，编译绝无此速度） |
| 脚本是否被重启 | 否 —— `=== 开始 ===` 在全文件中仅出现 **1 次** |
| 重复单元 | `日志末尾 10 行` 这行字，从 offset 15876 起**每 404 字节重复一次**，重复约 **2.39 亿次** |
| 文件尾部 | 全为 NUL 空字节（磁盘写满后写入失败的残迹） |

关键判据：**脚本只执行了一次流程，但输出内容被复制了 2 亿多次** —— 这说明"重复"不是脚本循环造成的，而是单条命令自身在循环。

## 3. 机制：为什么 `tail` 会自噬

```
        ┌─────────────────────────────────────────────┐
        │                                             │
        v                                             │
   tail -10 LOG  ──读末尾 10 行（404 字节）──►  输出
        ▲                                             │
        │                                             v
        │                                    >> LOG（追加回同一文件）
        │                                             │
        │                                             v
        └────── 文件变长，读位置仍未到新末尾 ──────────┘
```

`tail` 要输出"最后 N 行"，就必须**读到文件真正的结尾**才敢确定哪几行是最后 N 行。

当输出被追加回同一个文件时：

1. `tail` 读到位置 P，输出 404 字节；
2. 这 404 字节被追加到文件末尾 —— 文件的"末尾"向后移动了 404 字节；
3. `tail` 的读位置还没到达新的末尾，于是**它又读到了刚写进去的那 404 字节**；
4. 回到第 1 步。

**这不是"慢慢攒"，而是正反馈** —— 写出去的东西立刻变成要读的东西。像复印机对着自己印。

GNU 的 `tail` 不这样，因为它在打开文件时**记录初始大小/初始 EOF 位置**，读到那个位置就停 —— 之后追加进来的内容它不管。uutils 的实现显然没有这层"初始边界"。

## 4. 最小复现

```bash
# 造一个 > 7.5 KB 的文件（关键：小文件测不出来，见第 5 节）
python3 -c "
import io
io.open('log.txt','w').write('\n'.join('line %04d' % i for i in range(400)) + '\n')
"

# 危险写法
{ tail -10 log.txt; } >> log.txt

# 观察：GNU 版本 → 文件只涨 480 字节；uutils 版本 → 文件无限增长直到磁盘满
```

**安全起见请先封顶**（本次实验的做法）：

```bash
( ulimit -f 30720; { tail -10 log.txt; } >> log.txt )   # 单文件限制 30 MB
```

---

## 5. 触发阈值：约 7.5 KB

这是最容易被低估的一点 —— **小样本测不出来**。

| 文件大小 | uutils `tail` 的行为 |
|---|---|
| 几十字节 | 完全正常（轻微翻倍） |
| 约 7.5 KB 以下 | 正常 |
| **超过约 7.5 KB** | **开始无限自噬** |

作者最初的复现实验用了一个 10 字节的小文件，结果"一切正常"，差点得出错误结论（"脚本结构本身不失控"）。换成 48 MB 的真实文件后才复现。

**教训：验证这类行为必须用真实尺寸的样本。**

## 6. 对照实验：GNU vs uutils

方法：从软件源下载 GNU coreutils 的 `.deb`，用 `dpkg-deb -x` 解包到临时目录（**不安装、不替换系统工具**），跑同一实验。

| 实现 | 起始大小 | 结束大小 | 判定 |
|---|---|---|---|
| **uutils 0.8.0**（系统默认） | 19,200 B | **31,457,280 B**（被 ulimit 拦在 30 MB） | **失控** |
| GNU 9.4（Ubuntu 24.04） | 19,200 B | 19,680 B | 正常 |
| GNU 9.7（Debian） | 19,200 B | 19,680 B | 正常 |

- GNU 两次都是 `+480` 字节（正好是 10 行的输出），追加一次即停。
- uutils 一路涨到 `ulimit` 上限。

**结论：这是 uutils coreutils 0.8.0 独有的行为，不是"所有 tail 都这样"。**

### 为什么官方 CI 一直没发现

Cardinal 的官方 Windows 构建跑在 `ubuntu:22.04` 容器里 —— 那是 **GNU coreutils**，永远不会触发。而 Ubuntu 26.04 已经用 uutils 接管了 `/usr/bin/*`：

```
$ dpkg -S /usr/bin/tail
coreutils-from-uutils: /usr/bin/tail
$ ls -l /usr/bin/tail
/usr/bin/tail -> ../lib/cargo/bin/coreutils/tail     # 11 MB multicall 二进制
$ dpkg -L coreutils
/usr/share/doc/coreutils/changelog.gz                # GNU 二进制已被整体移除，只剩文档
```

## 7. 正确写法

**规则：任何命令的输出，绝不能重定向到它正在读的文件。**

三种安全写法：

```bash
# 写法 A（推荐）：先取到变量，再写
OUT=$(tail -10 "$LOG")
{ echo "$OUT"; } >> "$LOG"

# 写法 B：写临时文件再合并
tail -10 "$LOG" > "$LOG.tmp"
cat "$LOG.tmp" >> "$LOG" && rm "$LOG.tmp"

# 写法 C：日志只写不读 —— 汇总信息输出到 stdout，不要回灌日志
grep -c 'error' "$LOG"          # 直接打印，不重定向回 LOG
```

实测验证（写法 A）：17,500 字节 → 17,770 字节，**正常**。

### 配套的三条纪律

1. **日志文件只写不读。** 汇总/统计类输出一律打到 stdout 或另一个文件。
2. **复现这类行为必须先 `ulimit -f <KB>` 封顶**，别拿真磁盘当试验场。
3. **长任务必须挂磁盘水位哨兵。** 本次事故中，脚本连跑 8 轮编译，一次 `df` 都没看过 —— 所以它涨了 127 秒都无人察觉，直到虚拟机起不来才发现。

## 8. 影响面

- **谁受影响**：任何在 Ubuntu 25.10 / 26.04 及以上写 shell 脚本的人。uutils 已经开始接管默认 `coreutils`，覆盖面只会扩大。
- **什么写法会踩**：`{ ...; tail ...; } >> samefile`、`tail -f log >> log`、以及任何"输出目标 = 输入文件"的组合。
- **为什么危险**：这类反模式**过去最多是个小错误**（输出少量重复内容），现在升级为**磁盘瞬间占满**。属于典型的行为劣化放大。
- **可用的护栏参考**：GNU 的 `sort` / `shuf` 会主动检测并拒绝 `input file is also the output file`。`tail` 也完全可以加同类检查 —— 在检测到输出 fd 与输入文件相同时直接报错退出，而不是无限自噬。

---

## 9. 给 uutils 的反馈要点

1. **最小复现**：`{ tail -10 f; } >> f`，f 大于约 7.5 KB。
2. **期望行为**：与 GNU 一致 —— 只输出初始 EOF 之前的最后 N 行，追加进来的内容不再读。
3. **实际行为**：无限自噬，直到文件系统写满。
4. **对照数据**：GNU 9.4 / 9.7 均正常（+480 字节）。
5. **建议**：即使认为这是"未定义行为"，也应加"输出文件 = 输入文件"的护栏并报错（可参考 GNU `sort` 的实现），因为后果从"轻微错误"变成了"磁盘写满"。
